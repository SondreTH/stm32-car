# stm32-car: Team 7 (Ninjago) autonomous car

Firmware for a university project (MR2006B Industrial Automation, Tec de
Monterrey). An STM32 NUCLEO-F446RE drives a small car with one DC motor
(rear), Ackermann steering by servo, a wheel encoder, an HC-SR04 sonar, an
MPU-6050, an I2C OLED and a Bluetooth serial module.

**Goal of the course project:** drive a circuit of about 150 m alone, stop
10 s at three waypoints, avoid obstacles, end at the start.

**Where the firmware is now:** straight distance runs with a trapezoidal
speed profile and a position PID, obstacle *stop* (not avoidance), manual
driving, OLED, telemetry. No gyro, no x/y position, no route following yet.

## Rules for working in this repo

- **Generated files.** `main.c`, `main.h`, `stm32f4xx_it.c` and
  `stm32f4xx_hal_msp.c` are generated by CubeMX from `stm32-car.ioc`. Only
  edit between `USER CODE BEGIN` and `USER CODE END`. Anything else is
  erased at the next code generation. Do not hand-edit `stm32-car.ioc`
  unless the matching generated code is changed with it; prefer telling the
  user what to change in CubeMX.
- **New code goes in new `car_*.c` / `car_*.h` files** in `Core/Src` and
  `Core/Inc`. CubeIDE compiles them automatically.
- **Keep the global variable names in `car_drive.c`** (`state`, `SP_Vel`,
  `Real_Dist`, `Pos_Ref`, `Kp`, `Ki`, `Kd`, `test_dist_m`, `ErrorAcum`, …).
  The team watches and sets them from STM32CubeMonitor, and they match the
  course slides (M2.9 speed profile, M2.10 PID).
- **Units:** cm, cm/s, seconds, motor in % (−100..100). Forward is positive.
- **No `printf` with `%f`.** newlib-nano has no float printf. Use the line
  builder in `car_comms.h` (`lb_str`, `lb_float`, `lb_send`, `say`).
- **Nothing in the main loop may block for long.** The OLED update (~25 ms)
  is the longest thing there. The control step runs in the TIM3 interrupt.
- **Code style:** the team are students, several of them new to C. Keep the
  code plain, comment why, and keep the references to the course slides.
- **Docs style:** short sentences, no jargon that the course did not use.
- **Commits:** the user commits without a `Co-Authored-By` line. Do not
  push or open PRs unless asked; the remote is a teammate's repository
  (`SondreTH/stm32-car`).

## Build and check

The team builds and flashes with STM32CubeIDE 1.17.0 (`Debug/` is generated
and ignored). The makefile in `Debug/` uses ST-only compiler flags, so it
does not work with a plain `arm-none-eabi-gcc`. From a terminal use:

```
tools/build_check.sh        # compiles everything into build/, -Wall -Wextra on car_*.c
```

It must finish with a size table and no warnings from `car_*.c`.

There are no unit tests. The position loop can be exercised on the PC:

```
gcc -O2 -Wall -Wextra -Itools/drive_sim -ICore/Inc tools/drive_sim/drive_sim.c \
    Core/Src/car_drive.c Core/Src/car_config.c -lm -o tools/drive_sim/drive_sim
tools/drive_sim/drive_sim d=1           # 1 m run, prints a one-line summary
tools/drive_sim/drive_sim d=0.1 start=70 off=52 slope=0.8 tau=0.45   # a different model car
```

Run it after every change to `car_drive.c`, over short and long distances
and a few model variations (see [docs/control.md](docs/control.md)). The
model is a guess at the real car, so it shows logic errors and relative
changes, not real centimetres. **Nothing here replaces a run on the car;**
say clearly what was only simulated.

## Things that are easy to get wrong

- `drive_update()` runs in an interrupt. Starting a run from the main loop
  must go through `drive_start()`, which masks TIM3 while it sets up.
- TIM3 does two jobs: its update interrupt is the 100 ms control step, and
  its counter (10 µs per count) times the sonar echo. Changing its
  prescaler or period breaks both `DRIVE_PERIOD_MS` and `SONAR_TICK_US`.
- The position loop needs the encoder to count **up** when driving forward
  (`ENCODER_INVERT`). The old code used the absolute value and did not care.
- The motor needs about 60 % to start moving but less to keep rolling. Any
  new code that commands the motor from standstill must go through
  `Apply_Motor_PWM()` in `car_drive.c` (or reuse its kick-start idea).
- `BATT_DIVIDER` (6.58) does not match the wiring guide (4.03). See
  [docs/hardware.md](docs/hardware.md).
